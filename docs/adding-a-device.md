# 加一台设备

这份文档写给「想让自己的设备被 PowerRing 认出来」的人。**不需要会写代码**，需要的是耐心和一个能对照的官方软件。

整个过程分五步，前一两步通常十分钟能走完，真正费时间的是第四步「标定」。

---

## 第 0 步：先确认这台设备值得一试

满足这三条里的任意一条才可能成功：

- 有**官方软件能显示电量**（G HUB、NGENUITY、雷云、Armoury Crate 之类）。它能读出来，说明数据一定到了电脑上，只是不给你用而已
- **网上有人逆向过**它（搜「设备型号 + hid battery」「设备型号 + reverse engineering」）
- 是 **HID++ 设备**（罗技系），这类直接走通用协议，不用逆向

这三种都做不到的，建议开 Issue 让社区一起想办法，别一个人硬啃。

> 蓝牙设备（比如 AirPods）目前不支持：它们的电量走 BLE GATT，由系统自己管理。

---

## 第 1 步：找到设备暴露的接口

一台 USB 无线设备往往向系统开放好几个 HID 接口（键盘部分、鼠标部分、厂商自定义部分……）。**电量请求通常只在其中一个上有回应**，找错接口的表现是「发了报文，对面一声不吭」。

仓库里带了探测脚本，先装依赖：

```bash
pip install hidapi
```

然后列出你设备上的所有接口：

```bash
# 不知道 vendor id 就什么都不加，看全部
python tools/probe.py list

# 知道的话直接过滤，vendor id 可以在设备管理器 → 硬件 ID 里看到 VID_xxxx
python tools/probe.py list --vid 0x0951
```

输出长这样：

```
== 0x0951:0x1723  HyperX Cloud Flight Wireless
   usage_page=0x000C usage=0x0001  iface=3
   usage_page=0xFFC0 usage=0x0001  iface=3
   usage_page=0xFF90 usage=0x0303  iface=3     <-- 真正有回应的那个
   usage_page=0xFF00 usage=0x0001  iface=3
```

把这四个数字（`0x0951`、`0x1723`、`0xFF90`、`0x0303`）记下来，它们就是 YAML 里 `match:` 那一段。

**别忘了设备必须是开着的。** 接收器一直插在电脑上，无论耳机开不开机它都会被枚举到 —— 所以「开着时所列举不出来」不代表设备不存在。

---

## 第 2 步：找到那条「问电量」的报文

这是唯一有技术含量的地方。三条路，从上往下试：

**① 抄公开资料（最快，优先）**

搜开源项目里已经整理好的常量。常见的有 Solaar（罗技）、kondinskis/hyperx-cloud-flight（HyperX 天箭）、HeadsetControl、OpenRazer。你要的不是代码，是**那几个数字**：请求发什么字节、响应第几个字节是电量。

> ⚠️ **许可证红线**：可以抄事实（这些报文值、feature 号属于对硬件行为的描述，就像 CPU 指令表），**不可以抄代码**。为此每份 YAML 都必须填 `protocol_source` 写清楚出处。GPL 项目的常量照抄是允许的，但别把它的 Python/C 函数搬进来。

**② 让脚本去撞（适合请求格式简单的设备）**

拿到 ID 之后可以让脚本把每个接口、每种常见 report id 都试一遍：

```bash
python tools/probe.py scan --vid 0x0951 --pid 0x1723
# 或者你自己指定要试的报文
python tools/probe.py scan --vid 0x0951 --pid 0x1723 --cmds "21 FF 05,06 FF 05"
```

有回应的组合会打印出来：

```
## usage_page=0xFF90 usage=0x0303  有 1 条请求得到响应
   发 21 FF 05 00 ...           -> 回 21 FF 05 0E E7 00 ...
```

> ⚠️ 别在主力外设上扫太久，也别错过太大的 report id —— 天箭的电量请求用的是
> `0x21`，比常见的 `0x00`–`0x10` 都大，当初就是按顺序试漏了它，白折腾了一轮。
> 找不到就换个 id 上限再试，或者干脆走第 ③ 条。

**③ 抓包（最可靠，也最麻烦）**

用 Wireshark 抓 USB HID（Windows 上要装 USBPcap），在有官方软件的情况下打开它，看它发出去的是什么字节。这是最硬核但最不会骗人的办法。

## 第 3 步：写声明

到 `devices/` 下复制最接近的一份 YAML，改这几处。罗技系走 `hid++2.0`，其他统统走 `raw`。

### 通用字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | ✅ | 设备全名，显示在左键面板里 |
| `short` | | 悬停 tooltip 用的短名。多个设备悬停文字会拼在一起，全名太长的话填一个，如 `GPW` / `Cloud Flight` |
| `protocol` | ✅ | `hid++2.0`（罗技）或 `raw`（其他） |
| `transport` | ✅ | `receiver` = 经接收器按 slot 寻址；`direct` = 直连（含自带接收器已配对成一台的情形） |
| `match` | ✅ | `vendor_id` / `product_id` / `usage_page` / `usage`，第 1 步拿到的四个值 |
| `slots` | | `receiver` 模式下要探测哪些槽位，默认 `1..6` |
| `identify` | | `name_feature` + `contains`：读设备名做二次确认，避免同一接收器上的别的设备被误认 |
| `protocol_source` | ✅ | 报文常量的出处。**必须填**，这是许可证红线的凭证 |
| `verification` | ✅ | `verified`（上过真机）或 `unverified`（还没验证） |
| `notes` | | 踩过的坑写在这里，后人会感谢你 |

### `protocol: hid++2.0` 时

```yaml
battery:
  feature: "0x1001"    # 电量 feature 号
  kind: "voltage"      # voltage = 读到 mV 再换算；percent = 读出来就是百分比
```

### `protocol: raw` 时

```yaml
battery:
  request: "21 FF 05"         # 请求字节，空格分隔，首字节是 report id
  reply_len: 20               # 报文长度。很多设备按长度过滤，短了干脆不回
  state_index: 3              # 响应里「档位」字节的下标（从 0 数）
  value_index: 4              # 响应里「数值」字节的下标
  charging_states: ["0x10", "0x11"]   # 档位取这些值时表示正在充电
  table:                      # 档位 → 分段换算表
    "0x0e":
      - [89, 10]              # 数值 ≤ 89 算 10%
      - [239, 60]             # 数值 ≤ 239 算 60%
      - [255, 65]
    "0x0f":
      - [19, 70]
      - [255, 100]
```

**为什么用分段表而不是公式**：这些设备的原始数值跟百分比**不是线性关系**。天箭那边做线性拟合时，高电量段能差出十几个百分点 —— 别偷这个懒。

## 第 4 步：标定（别跳过）

拿到数值之后还剩一件事：**这个数字对应百分之几？**

做法很笨但有效：

1. 打开官方软件，让它显示当前百分比
2. 记下此刻 PowerRing 日志里的原始数值（`%APPDATA%\PowerRing\log.txt`）
3. 正常用这台设备一整天，每隔一两个百分点重复一次
4. 把 (原始数值, 真实百分比) 这些点连起来，就是你的 `table`

采样点越密越好。**没标定过的设备请把 `verification` 写成 `unverified`** —— 这样别人看到就明白这份数据还没验证过，而不是当成可信数据用。

只想贡献一部分数据也完全没问题：Issue 里贴 (数值, 百分比) 对照表，标定这步可以交给别人继续。

---

## 第 5 步：验证并提交

把 YAML 放进 `devices/`（和 exe 平级的那个目录），重启 PowerRing，看托盘环亮起来了没有。

检查三件事：

- [ ] 圆环不是灰的（灰色说明读不到）
- [ ] 数值和官方软件对得上（允许有 1–2 个百分点的出入）
- [ ] 设备关机后能自动从列表里消失，不会挂着旧数字

然后提 PR。PR 里请带上：

- `protocol_source` 的来源链接
- 至少一组「PowerRing 读数 vs 官方软件读数」的对照
- 若 `verification` 是 `unverified`，说明为什么没能验证

---

## 常见翻车点

| 现象 | 多半是这里 |
| --- | --- |
| 托盘一直是灰环 | 接口选错了。回到第 1 步，把 `usage_page` / `usage` 逐个换着试 |
| 灰环但在 Bus 上看得到设备 | 设备关机了，或者报文长度不对（试 `--len 7` / `--len 20`） |
| 读数乱跳 | 原始值本身有抖动。检查是不是正好落在 `table` 的分段边界上，抖一下就跨档 —— 把那一段拉宽一点 |
| 显示 0% 但实际有电 | 别慌 —— 程序不会用 0% 表示读不到，读到 0 说明 `table` 的最后一档配错了 |
| 同一接收器上的别的设备也被当成了它 | 补 `identify.contains` |
